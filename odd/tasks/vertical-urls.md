# Vertical folders and URLs

## Objective

Give every editorial vertical its own content folder and URL segment so the
news portal is organised topically and Google can index it more efficiently,
**without changing a single already-published URL**.

| | Existing (664 ES / 44 EN) | New |
| --- | --- | --- |
| ES folder | `news/<slug>/` | `news/<vertical>/<slug>/` |
| `entry.id` | `<slug>` | `<vertical>/<slug>` |
| ES URL | `/noticias/<slug>/` | `/noticias/<vertical>/<slug>/` |
| EN URL | `/en/news/<slug>/` | `/en/news/<vertical>/<slug>/` |
| Hub | — | `/noticias/<vertical>/` · `/en/news/<vertical>/` |

The folder name **is** the vertical token **is** the URL segment. No new
frontmatter field: the folder is the single source of truth.

## Problem / Why

- Today the folder name is the whole URL (`entry.id = basename`), so every
  article sits flat under `/noticias/<slug>/`. There is no topical structure
  for crawlers and no internal linking between a vertical and its articles.
- 664 Spanish + 44 English articles are already published and indexed. The
  existing URL must not move, so the change is **go-forward only**: legacy
  entries keep their flat folder and flat URL.

## Constraints

- Astro 7 static output. Named dynamic route params take precedence over rest
  params (verified in the Astro routing docs), so `[vertical]/[slug].astro`
  and `[...page].astro` coexist.
- A content `id` containing `/` must go through a route whose params match one
  segment each; the id is split in `getStaticPaths`, never passed whole to a
  single named param.
- Hub and legacy article both live at `/noticias/<one-segment>/`, so they must
  be generated by **one** route file (`[slug].astro` dispatcher) — two files
  with the same pattern would be ambiguous.
- No URL, slug or title changes for legacy content. No content edits. No new
  dependencies. No content-file moves.
- Every consumer that already builds `/noticias/${entry.id}/` keeps working
  unchanged because the id now carries the vertical.

## Scope

- In: `src/lib/verticals.ts` (new), `src/lib/related.ts`,
  `src/components/{ArticleView,ArticleViewEn,VerticalHub,NewsCard}.astro`,
  `src/pages/noticias/{[slug],[vertical]/[slug]}.astro`,
  `src/pages/en/news/{[slug],[vertical]/[slug]}.astro`, `astro.config.mjs`,
  `scripts/{slug-check,find-published,index-published,validate-sitemaps}.mjs`,
  `AGENTS.md`, `skills/redaccion-prensa/{SKILL,DELEGATION}.md`.
- Out: moving or editing any legacy content, `rss.xml.js`, `buscar.json.ts`,
  `news-sitemap.xml.ts` (all use `${entry.id}` and need no change), the
  card/lead components other than the `basePath` generalisation.

## Acceptance criteria

      `/en/news/<slug>/` unchanged.

      `/en/news/<v>/<slug>/`, with correct canonical and hreflang.
- [ ] Hubs exist at `/noticias/<v>/` and `/en/news/<v>/` for verticals with
      published articles, linked from every article of that vertical.

- [ ] `crawlable` sitemap includes hubs and nested articles; `news-sitemap`

      regenerates with nested URLs.
